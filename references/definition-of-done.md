# 行为的定义

 一个站立的、全项目范围的栏杆,每个变化都必须在按规定计算之前明确。 与接受标准不同,每个任务都不同,回答“我们造了正确的东西吗?” 不同的是,“完成”的定义每一次和回答“这是否完成了我们的标准?” `planning-and-task-breakdown`, `incremental-implementation`,以及 `shipping-and-launch`.

## D. 定案的定义与接受标准

| | 接受标准 | 行为的定义 |
|---|---|---|
| 范围 | 特定任务或规格 | 适用于每次递增 |
| 变动 |  每个项目都不同 | 固定和再利用 |
| 答复 | "我们是否建立了 *这件事情*?" | "是吗? *准备*?" |
| 拥有者 | 任务规划时的定义 |  为项目定义一次 |
| 示例 | "用户可以通过电子邮件链接重置密码" | "测试通过,没有回归,文档更新" |

两者是相辅相成的,只有在以下情况下才能完成一项任务: **编号** 符合验收标准 **财务报告和财务报告** 符合“完成”的定义。跳过看来已经完成但还没有完成的工作。

## 常设核对表

 在宣布完成前, 应用到每个更改 。

### 正确性
- [ ] 任务的所有接受标准都得到满足
- [ ] 代码运行和行为符合预期,在运行时进行校验,而不仅仅是编译或输入检查
- [ ] 新的行为被测试覆盖 没有改变就失败了 随它而通过
- [ ] 现有测试仍然通过;没有引入回归
- [ ] 边际案件和错误路径得到处理,而不仅仅是幸福路径

### 质量
- [ ] 守则通过命名和结构显示意图;不需要任何评论来解释 *怎么样?*  没错
- [ ]  没有重复的业务逻辑
- [ ]  没有留下的已死代码、 调试输出或注释输出块
- [ ] 更改范围为任务范围;没有无关的重构符 。
- [ ] 调整和格式化通行证

 这些物品背后的深处 `code-review-and-quality` ( 五轴审查) 财务报告和财务报告 `code-simplification` ( 在不改变行为的情况下减少复杂性).

### 一体化
- [ ] 变革与系统的其他部分合作,而不仅仅是孤立无援
- [ ] 计算数据库迁移、配置变化和特征标记
- [ ] 任何公共接口的后向兼容性或 API 变动

### 文档
- [ ] 公共界面、 API 和用户行为记录
- [ ] 值得保存的建筑决定记录在案 ( 见 `documentation-and-adrs`)
- [ ] 文档用无时语言描述当前状态,而不是变化历史

### 船舶准备状态
- [ ]  审查任何不可信输入、认证或数据处理的安全影响 ( 见 `security-and-hardening`)
- [ ]  新关键路径的可观察性到位 (日志、指标、痕迹) ( 见 `observability-and-instrumentation`)
- [ ] 任何有风险的东西都存在回滚路径 ( 见 `shipping-and-launch`)
- [ ] 人类在合并或部署前已经审查并批准

## 如何应用

- ** 每个任务**:在检查任务之前确认正确性和质量部分。
- ** 每个特性**: 在考虑完成特性之前确认整合和文件。
- ** 每一次释放**: 完整的核对表为底稿; `shipping-and-launch`  在顶部增加特定部署的大门.

将列表修改一次, 然后不加修改地重用它。 重新谈判每次短跑的“ Done” 定义不是“ Done” 定义 。

## 红旗

- "已经办好了,我只是还没有办好":未经核实的工作还没有完成.
- “ 测试通过” 用作完成的同义词, 而文件、 回归或运行时的校验被跳过 。
-  根据最后期限的压力,适用了不同的条。
- 接受标准作为全条条处理,不设常备质量底板.
- "提出"在人类审查需要它的变化之前宣布.
