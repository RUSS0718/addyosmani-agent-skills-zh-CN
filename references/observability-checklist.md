## 电话问题 ( 从这里开始)

毫无疑问的遥测是噪音,在仪表前:

- [ ] 2 -4个问题 一个待召工程师会问 关于这个功能 被写下来
- [ ] 地图下的每一个信号 都指向其中一个问题
- [ ]  每个问题都匹配到正确的信号类型: 度量符表示 ** 那个**  有些事不对劲 痕迹说 **地点**,日志说 ** 为什么**

## 结构化日志

- [ ] 日志的结构 (JSON) 带有稳定事件名称的 – 而非自由形式字符串
- [ ]  每条日志都包含一个 correlation/request 系统边界上生成或接受的ID
- [ ] 在每个出入口的呼叫和同步边界上宣传关联ID (HTTP  页眉,队列元数据)
- [ ] 由多个入口撰写的日志流 (调度器、 重播终点、 手动运行) 包含一个切入点字段, 设置运行起始位置, 并附带相关 ID 。
- [ ] 日志级别一致 : `error` =无常断裂,有人可能采取行动; `warn` = 已退化但已处理; `info` - 重大商务活动; `debug` = 生产时停产
- [ ] 任何日志行中都没有任何秘密、标志、密码或未编辑的 PII (硬规则从 `security-and-hardening`)
- [ ] 允许输入字段——没有完整字段 request/response 机构,没有认证头
- [ ] 仅输入元数据的外部服务电话:端点、状态、耐久性、尝试计数、消毒识别器
- [ ] 实际日志输出当场检查:结构化字段,不 `[object Object]`

## 度量衡

- [ ] **红色**  每个终点和每个外部依赖的仪器:比率、误差、持续时间
- [ ] **用户**  为每种资源设置了仪器 (队列、 池、 主机): 利用、饱和、错误
- [ ] 纬度是直方图; p50/p95/p99  可查询——永远不平均
- [ ]  所有标签都来自小的,固定的套件 (路由模板、状态类、提供者名称)
- [ ]  没有未绑定的标签值:没有用户ID,租户ID,电子邮件,原始 URL,请求ID,或错误消息文本
- [ ]  按类别分类的状况代码 (`5xx`,没有 `503`)
- [ ] 跟踪每个区域的深度和处理时间 worker/queue

## 分布式追踪

- [ ] OpenTelemetry (或相当)  在服务启动时,在其他进口之前初始化
- [ ] 启用自动仪器 HTTPgRPC 和 DB 客户端
- [ ]  每一次外出通话都播放追踪上下文 (W3C 维基月球 `traceparent`/`tracestate`)  从每一个入境请求中提取
- [ ] 上下文可以幸存 Aync 边界——队列消息携带痕量元数据
- [ ] 手册仅涉及有意义的内部工作单位,待调用属性将由
- [ ]  没有跨度属性的秘密或 PII 属性
- [ ] 低默认率进行头部取样;如果有尾端取样,则100%保留错误

## 警报

- [ ] 每一个警报都是基于症状的 (错误率, p99 延迟, 队列年龄) - 原因 (CPU, 磁盘, 重新启动)  去仪表板,不是寻呼机
- [ ] 每一个警报都是可操作的;"忽略它,它自愈"的警报被删除.
- [ ]  每个提醒链接到一个运行本——至少三行:它意味着什么,第一个运行的查询,升级路径
- [ ] 由 SLO 或历史数据证明合理的阈值和持续时间, 不猜测
- [ ]  只有两个断层: ** 页 次** (显示用户身份, 现在就行动) 财务报告和财务报告 **门票** (堕落,本周行动)
- [ ]  每个新警报试射一次:它到达了正确的频道和运行本链接工作
- [ ]  没有警报,每天开火 和得到承认,没有行动

## 电线板

- [ ] 服务健康仪表板存在:误差率、延迟p99、流量、饱和度
- [ ] 依赖性保健小组显示人均服务误差率和耐久性
- [ ] Dashboard从本清单的顶端回答待命问题——不是"除了答案之外的一切".
- [ ] 默认时间范围很合理 (1小时-6小时,而不是30小时d)

## 校验遥测

仪器是代码,可能是错误的:

- [ ] 强制操作错误 + 在日志中找到它 以相关 ID 找到它
- [ ] 发送测试流量 − 度量序列出现预期标签和正常值
- [ ]  在追踪中遵循了1项要求的端到端 UI - 没有断裂的跨度
- [ ] 仅通过遥测就诊断出诱发性衰竭,而未读取来源

## 洛阳前门

 在进行生产之前,以下所有情况都是真实的:

- [ ] 结构化日志流到日志集合器
- [ ]  每个新的终点和依赖性在仪表板上可见的RED指标
- [ ] 配置至少一个基于症状的提示, 包含运行本, 试射
- [ ] 请求可以追踪到它触及的每一项服务
- [ ] 待命时知道本子在哪

 关于发射日监测序列和回滚触发器,见 `shipping-and-launch` 技术。
