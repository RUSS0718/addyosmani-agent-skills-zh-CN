# 采纳指南:新项目与既定守则库

如何推出代理技能在很大程度上取决于你生命中的代码库。 一个绿地项目可以从承诺中引入整个生命周期。 一个历史悠久的代码库需要一个渐进路径,尊重已经存在的东西,它的公约,它的无证决定,以及它缺乏在你不愿触摸盲点的测试覆盖。

 本指南涵盖两条路径。关于安装机械,请参见: [启动( M)](getting-started.md) 和各种工具的配制。每种技能所行的善功,你看看! [README 中的技能目录](../README.md#all-25-skills).

---

##  你走哪条路?

| 信号                     | 绿地                      | 布朗菲尔德                                   |
| -------------------------- | ------------------------------- | -------------------------------------------- |
| 密码库的年龄            | 日数至周数                   | 月数与年数                              |
| 测试覆盖率              |  你从第一天开始控制它     |  不均匀; 一些区域未测试                  |
| 公约                | 说定了,说定了               | 已建立,往往没有证件              |
| 团队习惯                | 编组                         | 收缩 (不论好坏)             |
| 更换不良剂的风险 | 低爆炸半径                |  能打破一切 没有人记得如何修复 |
| 收养战略          | ** 全生命周期,立即** | **递增、核查-第一**          |

 如果你在中间的某个地方 (已经投产的年轻项目),从棕田路径开始加速,它在同一端状态上汇合.

---

## 路径 A | 绿地:从第一天起的整个生命周期

一个新项目是最好的情况:没有遗留行为可以保存,因此技能的质量门几乎一无所有,并且从第一次承诺开始复合.

###  第 0 日 时 间 | 安装和电线

1. 安装包 (`npx skills add addyosmani/agent-skills`,或工具的本地融合,参见 [启动( M)](getting-started.md)).
2.  如果主机没有本地技能路由器, 请加载 `using-agent-skills` (元技能)  因此代理可以自行将工作导向合适的技能. 在主机上安装本地的路由,安装个人的技能,并且不会像常上下文那样预先加载元技能.
3. 添加一个简短的项目规则文件 (`CLAUDE.md`, `.cursorrules`, 等 (简体中文).) 与你的堆栈,命令,和边界, `context-engineering` 描述属于那里的东西。

###  第 0 日 时 间 |  在构建前定义

 为项目的第一个真实功能运行寿命周期 :

```
/spec   →  SPEC.md            (spec-driven-development)
/plan   →  tasks/plan.md      (planning-and-task-breakdown)
/build  →  one slice at a time (incremental-implementation + test-driven-development)
/review →  before every merge  (code-review-and-quality)
/ship   →  when going live     (shipping-and-launch)
```

`/build auto` 适合绿地:你只批准一次计划,每项任务仍由测试驱动,并单独承担。 (`SPEC.md`, `tasks/`)  如果特性跨越一个以上的会话,这些文件也是交接文件,请查看 [跨届会工作](getting-started.md#working-across-sessions).

###  从一开始,就把这些当做常客

- **test-driven-development**,覆盖债务最便宜 避免在零。
- **git-workflow-and-versioning**,原子承诺和~100线的变化是习惯,而不是改造.
- **security-and-hardening**, 认证, 输入验证, 和秘密处理都是结构性的; 后期锁定它们是一个迁移项目 。
- **documentation-and-adrs**最早的建筑决定 就是没人会记得的 _ 为什么_ 两年后。 ADR  现在阻止了B路所描述的棕原考古学.

###  随着工程的增长而添加

| 何时                                | 装入                                                          |
| ----------------------------------- | ------------------------------------------------------------- |
| 第一次公开 API 或模块边界 | `api-and-interface-design`                                    |
| 第一届 UI 工作内容                       | `frontend-ui-engineering` (+ `browser-testing-with-devtools`) |
| 第一届 CI 输油管                   | `ci-cd-and-automation`                                        |
| 第一次生产部署             | `observability-and-instrumentation`, `shipping-and-launch`    |
| 所需业绩出现     | `performance-optimization`                                    |

### 绿地反标

- **跳过 `/spec`  因为"它只是一个原型。"** 原型成为产品,这是你为这个密码库写过的最便宜的文物。
- **将全部25种技能装入每个会话中.**  它浪费了上下文,并稀释了重要的上下文。 逐个装入; 让主机的本地路由器或 `using-agent-skills` 路线,但不是两者。
- **将观察力推迟至"有东西可观察".**  在你建造的仪器, 改造结构化的日志 是一个你选择创建的路径 B 的问题。

## 路径 B | Brownfield:增量,核查-第一

 在既定的代码库中,风险简介倒置: 危险不是造错东西,而是 _变化_  因此,领养令的起始技能是: **阅读和保护** 代码库, 并且只是后来移动到 技能 **变动**  这个。

### 第一阶段 |  背景和只读技能

目标:特工在修改任何内容之前会理解密码库.

1. **`context-engineering`  先说.** 写入项目规则文件, 描述真正的公约, 代码中的公约, 而不是 wiki 中的公约。 包含 build/test 命令、目录含义、已知地雷 ("别碰" `legacy/billing` 它没有测试 和三个已知的工作。").
2. **`code-review-and-quality` 的更改。**  审查是零风险和立即有价值的:五轴审查及其严重性标签 ( 它能区分什么阻断合并 关键和需要 与什么没有)  无论密码库的状态如何 在任何公关上工作
3. **`debugging-and-error-recovery`  你正在修复的虫子。** 5步分解法 5步分解法 (复制 · 本地化 · 减少 · 固定 · 警卫) 闪耀在陌生的代码中,"守护"步骤开始建造你没有的回归套房.
4. **`doubt-driven-development`  作为安全网.** 遗产代码正是"不熟悉的代码,错误的高昂成本"的情景中这种技能目标. 对代理商关于遗产系统如何运作的说法进行反常的新鲜文字回顾,在他们成为罪犯之前就能够捕捉到自信的幻觉.

###  第2阶段 | 更改前的测试

目标:代理商触及的每个区域都会先获得一个安全网.

- **`test-driven-development`,有选择性地应用。**  不以全球覆盖为目标;以覆盖为目标 _计划进行更改的地方_。对于未经测试的遗留行为,在任何修改之前,写出特征测试、确定代码当前所做所为(对错)的测试。 Beyonce Rule 应用:如果代理人喜欢一个足以依赖它的行为,那么就应该对它进行测试.
- **`code-simplification`  在最严重的热点。** Chesterton's Fence 执行原则是:技能迫使代理人理解 _ 为什么_ 代码在删除它之前就已存在。行为保存简化加特征测试是使遗留代码可以更改的最小风险方法。
- **`git-workflow-and-versioning`  无处不在。**  小原子会犯事 _更多( E)_  在布朗菲尔德语中:当对旧代码的修改打破一些微妙的东西时,一个~100线的承诺是可分化的;一个2000线的"现代化"的承诺不是.

###  第3阶段 |  新工作贯穿整个生命周期

目标:双速通过,遗留守则保留在第一阶段至第二阶段制度之下; ** 新功能获得绿地治疗**.

- 旧密码库的新功能? `/spec → /plan → /build → /review`。 spec's 边界部分是您在其中声明该特性可能和可能不会触及的遗留物。
- **`api-and-interface-design`  在缝合处。**  当新代码必须和旧代码交谈时,先设计边界合同. Hyrum's Law 在一个古老的密码库里,不是理论上的, 有人依赖于每一个可观察到的行为, 包括虫子。
- **`security-and-hardening`  作为审计,然后是大门。** 穿过现有攻击表面运行一次 (验证、输入处理、依赖性、依赖性审计通常为这项工作付费),将找到的东西存档,然后在新的更改上执行。

###  第4阶段 | 降薪、贬值、观察

- **`deprecation-and-migration`**  是Brownfield的优秀技能: 代码的可靠性,强制的 vs. 咨询的堕落, 和僵尸代码的去除 给你一个纪律的方法 缩小遗留的表面 而不是仅仅包装它。
- **`observability-and-instrumentation`** 沿着您实际调试的路径进行了改造: 结构化记录和RED 度量衡先在顶端事件源上进行。
- **`performance-optimization`**  当回归重要时,它的度量第一规则可以防止经典的遗留陷阱,即优化从来就不是瓶颈的代码.

### 布朗菲尔德反标

- **"大爆炸"收养.**  在第一日将整个生命周期装入遗留的代码库中, 生成已存在的代码的规格, 并重构没有安全网的代码。 按顺序排列 。
- ** 让代理重置未测试的代码 。**  没有特征测试, 没有重构。 这是棕色场收养中最昂贵的捷径 。
- **跳过 `context-engineering`  因为"代码是文件。"** 特工会从最糟糕的档案中推断出惯例 告诉真实的档案
- **将遗留系统的行为视为默认错误.** Chesterton's Fence: 奇怪的重试循环可能带有负载。 明白, 然后改变 。
- **拨乱反正** 收养应该能使质量单调更好:每个阶段都增加一个不会退缩的大门,如果在一个月里你无法说出现在执行的不是以前的东西,那么推出就已经停滞了.

##  两条路交汇

 两端都处于同样的稳定状态: `/spec → /plan → /build → /review → /ship`  为新工作,始终 TDD Greenfield在几天内到达; Brownfield在四分之一时间内到达, 区别就是安全网。 (上下文、特征测试、边界) 旧的密码库从来没有。

|                        | 绿地                     | 布朗菲尔德                               |
| ---------------------- | ------------------------------ | ---------------------------------------- |
|  第一技能已装入     | 原生路由器,或 `using-agent-skills` + `/spec` | `context-engineering`                    |
| 交付的第一价值  | Spec'd, 测试的第一个功能   | 零风险审查和更安全的错误修正    |
| TDD 态势            |  从承诺一开始普遍化      | 选择性:计划进行更改的测试 |
| 重构规则       | 稀有 (几乎没有要重构)      |  先进行特征测试,总是     |
|  最有风险的反模式  | 跳过光谱              | 重构未测试的代码                |
| 进入整个生命周期的时间 | 头一天                        | ~ 四分之一, 双速在中间       |
