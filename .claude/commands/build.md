## 模式

- **`/build`** - 执行 *下一个*  待决任务,然后停止 (小心点,一次一个切片).
- **`/build auto`** - 必要时制定计划,获得单一批准,然后执行 * 每张* 任务之间不中断。

`$ARGUMENTS` 选择模式。处理 `auto` (犬类) 或 `all`  作为自定义模式; 其他任何 (或为空)  是默认的单任务模式。注意: 自动模式不快 * 每个任务* ——它运行相同的测试驱动循环——它只清除了人类的脚步. *介于* 任务。

## 默认: 一个任务

 从计划中选择下一个待定任务。 然后 :

1. 读取任务的接受标准
2. 装入相关上下文 (已存在的代码、模式、类型)
3.  为预期行为写一个失败的测试 (红色)
4. 执行通过测试的最小代码 (绿色)
5. 运行完整的测试套件以检查回归
6. 运行构建以验证编译
7. 提交描述性信件
8. 标记任务完成并停止

## 自治:整个计划 (`/build auto`)

 一旦一个 spec 存在, 您想要崩溃计划 + 构建到一个运行中。 它会删除任务之间的手动步骤 。 - ** 没有** 每项任务仍然要经过考验,并有自己的决心。

1. **需要一个规格。** 仅查看已知路径的示意图 : `SPEC.md`  {\fn华文楷体\fs16\1cHE0E0E0}在雷波根 `docs/SPEC.md`,或下面的文件 `spec/`。读取或任意的博士 ** 没有** 数。如果不存在,请停止并告诉用户运行 `/spec`  第一,不要发明要求。
2. **建立干净的基线。** 运行 `git status --porcelain` 如果在预期规划文物之外有未承付的变动 (`SPEC.md`, `docs/SPEC.md`, `spec/*`, `tasks/plan.md`, `tasks/todo.md`)中,停止并请求用户承诺、藏匿或确认如何处理它们。每个任务自主承诺不得吸收无关的本地工作,或清除回滚保证中断。
3. **计划如果需要的话。**  如果没有 `tasks/plan.md`,引用代理技能:planning-and-task-breakdown 生成一个。
4. **单检点.** 提出完整的计划,等待明确的肯定 ( 例如"同意","去","是"). 处理被套期的反应 ("看起来很合理" "我想")  作为 ** 没有**  这是唯一的人类大门——在批准后,自主运行。 `tasks/plan.md`将它作为单一的准备承诺 现在,这样它就不会 流血到第一个任务的承诺。
5. ** 按依赖顺序执行每一项任务。** 使用每个任务已声明的依赖关系; 如果它们不是明确的, 按计划列出它们的顺序执行。 对于每个任务, 运行上方的全部默认循环 (RED 绿色 回归 建设 承诺 完成标记)。只处理任务所触及的文件加上任务状态更新 。 `git add -A` 盲目地——并让一个人承担每个任务,所以任何一点都是干净的退缩。
6. **停止并询问用户** ( 不要冲过去)  当:
   - 测试不能通过 或建筑间歇 没有明显的固定 ~ 遵循代理技能:debugging-and-error-recovery
   - 光谱是模糊的,或者任务需要决定,光谱不涵盖
   - 任务具有高风险或不可逆转性—— auth/permission 变化,破坏性数据迁移,支付,删除,部署,任何触摸到的秘密, **或任何你无法挽回的东西 `git revert`** - 学习代理技能:doubt-driven-development 并在继续前获得明确签注

   用户解决一个阻塞器后,它们会重新输入 `/build auto`  它从下一个待决任务开始。
7. **结尾摘要 :** 任务完成、测试添加、承诺和任何跳过、标记或留给用户的。

 如果任何步骤失败,请遵循代理技能:debugging-and-error-recovery 技术。
